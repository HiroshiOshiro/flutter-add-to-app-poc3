# 作業概要

既存のネイティブアプリ（iOS: Objective-C / Android: Java）に Flutter を組み込み、
Todo（メモ）の**確認画面だけ**を Flutter に置き換えた。最終的に全画面を Flutter 化
する前提で構成を決めている。

同時に、手順書 `MIGRATION_GUIDE.md` を上からなぞって「書いてあるとおりで本当に
動くか」を検証した。

| | |
|---|---|
| Flutter | 3.47.1（stable） |
| Androidの組み込み | source module |
| iOSの組み込み | Swift Package Manager |
| PR | 13本 |
| 見つけた手順書の欠陥 | 8件 |

節ごとの詳細は `WORK_LOG.md`、手順そのものは `MIGRATION_GUIDE.md`、
デバッグ手順は `DEBUGGING.md` にある。

---

## 1. 何をしたか

Todoフローは **入力 → 確認 → 完了** の3画面。このうち確認画面だけを移した。

移行後も画面の見た目と操作は移行前と同じ。ネイティブが保持している入力内容を
受け取って表示し、確定すると送信して、まだネイティブのままの完了画面へ抜ける。

**1画面だけ移す場合と、全画面を移す前提で1つ目を移す場合とでは、選ぶ構成が変わる。**
後者に寄せた。

| 項目 | 選択 | 理由 |
|---|---|---|
| Androidの組み込み | source module | 全員がFlutterを扱う前提のため。AARにすると配布の手間が増える |
| iOSの組み込み | Swift Package Manager | CocoaPodsはメンテナンスモードで、レジストリが2026年12月2日に読み取り専用になる |
| エンジンの持ち方 | `FlutterEngineGroup` | 画面ごとに独立したエンジンを持ちつつ、追加コストを1画面あたり約180kBに抑えられる |
| エントリポイント | `main()` ひとつ | 画面ごとに増やすと、画面を追加するたびにネイティブ側の起動コードも増える |

## 3. 手順書の検証結果

**0〜5節と7節は、書いてあるとおりで通った。**

今回のビルド失敗は0節のバージョン要件2件のみで、それも手順書の表から事前に
特定できた。前回の検証で追記した条件——リポジトリ設定、起動テーマ、初期ルートの
分割、Bridging Header——はいずれも**エラーを踏む前に**対処できている。

一方で8件の欠陥が見つかった。

| 種別 | 節 | 内容 | 現れ方 |
|---|---|---|---|
| **誤り** | 5.2 | エンジン生成のスニペットが `createAndRunEngine`。Dartが先に走り、チャネル登録が間に合わない | `MissingPluginException` |
| 不足 | 4.3 | プロジェクト再生成時にXcodeを閉じる指示がなかった | `Missing package product` |
| 不足 | 4.4 | Info.plistを生成している構成では、権限をDebugだけに入れる方法が自明でない | キーが反映されない |
| 不足 | 5.2 | チャネルをどこで登録するかが書かれていなかった | — |
| 不足 | 6.3 | ホストアプリの非公開フィールドは統合コードから参照できない | `is not public` |
| 不足 | 8.1 | ネイティブの画像リソースはFlutterから参照できず、チャネルでも渡せない | 画像が出ない |
| 不足 | 8.2 | 文言も同じ。対応しないとホストが英語でもFlutter画面だけ日本語のまま | 言語が揃わない |
| 不足 | 8.3 | `FlutterActivity` は `AppCompatActivity` ではないためActionBarが出ない | タイトルバーが消える |

**8件中5件が6節以降に集中している。** 実際にネイティブとやりとりして画面を作り込む
までは表面化しない種類のもので、配線だけを検証していた段階では見つけようがなかった。

8.3 はネイティブ側に手を入れた唯一の箇所。AppCompat系のテーマは
`windowActionBar=false` を指定していて、ActionBarは `AppCompatActivity` が自分で
立てている。`.Bridge` のテーマでも解決せず、プラットフォーム側のテーマを親にする
必要があった。

## 4. 全面移行を見据えた設計

1画面だけを見れば過剰に見える判断もあるが、いずれも「画面が増えたときに何が
増えるか」で選んでいる。

**画面を追加してもネイティブ側は増えない**

表示する画面はネイティブから渡す初期ルートで決める。Flutter化のたびに触るのは、
ルート名の定義と登録表への1行だけ。

**チャネルは画面単位ではなく機能単位**

`legacy_store` と `navigation` の2本。画面が増えてもチャネルは増えず、全面移行が
完了した時点で両方とも消える。

**アプリの外との通信はFlutter、ローカルデータはチャネル**

この分かれ目はRepository 1ファイルに閉じている。ViewModelもViewも、どちらが
どちらか知らない。

**ネイティブ抜きで動かせる**

チャネル越しの依存は差し替え可能にしてある。モジュール単体で起動でき、テストに
実機もネットワークも要らない。

## 6. 次にやること

入力画面と完了画面のFlutter化。起点はルート名の定義と登録表への追加で、ネイティブ
側の起動コードは増えない。**完了画面をFlutter化した時点で `navigation` チャネルが
不要になる。**

手順書側には、まだ埋めていない穴がひとつある。バージョン要件の表に
**iOSのDeployment Target** がない。生成されるSwiftパッケージがiOS 15.0以上を
宣言しているため、古いアプリでは最初に効く条件になる。
